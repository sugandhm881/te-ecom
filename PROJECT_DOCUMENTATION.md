## 1. Overview

Ecom Central is a single-server operations hub that unifies order management, shipping/courier tracking, delivery-performance analytics, warehouse operations, marketing analytics, and automated reporting for The Element's D2C business.

**Core responsibilities:**

- Aggregate orders from **Shopify** and enrich them with courier tracking from **RapidShyp** (primary 3PL aggregator) and **DocPharma** (secondary shipping platform).
- Track every shipment's full journey (dispatch → attempts → NDR → delivered/RTO) and compute delivery KPIs: FASR (First-Attempt Strike Rate), RTO rate, NDR recovery, TAT.
- Detect and escalate courier problems: silent RTOs (returned with no delivery attempt → freight claims), late deliveries (promise date broken), fake delivery attempts (manually flagged, AI-polished escalation emails).
- Run scheduled warehouse/ops reports into **Microsoft Teams** channels (native Adaptive Cards) with inbound keyword triggers via Microsoft Graph.
- Automate **Amazon review requests** with a human yes/no approval loop in Teams.
- Provide marketing analytics (Meta ad sets / ads / ranking) and profitability views.
- Multi-user access with per-dashboard, server-enforced permissions.

**Design principles**

- **DB-first reads:** dashboards read from synced Supabase tables; live courier APIs are called only to fill gaps (then cached back).
- **Single journey pipeline:** `app/api/delivery_journey.js` is the one parser/writer for `shipment_journey_ecom`; webhooks, backfills and crons all flow through it. Three delivery **sources** feed it: `rapidshyp` (webhook + scan timeline), `docpharma` (portal pull, milestones only), `kwikship` (nightly pull, `status_history` timeline — see below). All share the `saveJourney()` writer + `source` column; `PLATFORM_LABEL`/`platformLabel()` map source → display name.
- **Re-allocation cleanup (`supersedeStaleJourneys`):** the journey table is keyed by **AWB**, so re-allocating an order to a new AWB/aggregator (e.g. RapidShyp → deassign → Kwikship) would leave the OLD AWB's row orphaned — stuck non-final and **double-counting** the order in the dashboard/KPIs. After saving the current shipment's journey, every writer (`updateJourneyForOrder` for RS/DP, `updateKwikshipJourney` + the `kwikship-webhook`) deletes any other **non-final** journey row for the same `order_name` on a different AWB. A final (delivered/RTO) leg is always kept as history.
- **Kwikship (GoKwik) sync** — TWO paths, same as RapidShyp (real-time webhook + a cron backstop):
  - **Webhook (real-time):** GoKwik's dashboard *Merchant Webhooks* (Bearer-token auth; triggers Pickup Completed / OFD / Undelivered / RTO Initiated / Delivered) POST to the Supabase Edge Function **`kwikship-webhook`** (HTTPS; the Node app is HTTP-only, so — like `rapidshyp-webhook` — the receiver is an edge fn, `verify_jwt=false` + its own token check). On each event it fetches the authoritative `status_history` from Kwikship's API and upserts `shipment_journey_ecom` (source=`kwikship`). URL: `…/functions/v1/kwikship-webhook`. **Audit trail:** every hit is recorded in table **`kwikship_webhook_log`** (received_at, awb, order_name, cur_status, outcome, result, **user_agent**, source_ip, raw **payload**) — so it's provable which hits are real GoKwik events (their UA ≠ a manual `curl`) and it captures GoKwik's real payload shape. Query: `select * from kwikship_webhook_log order by received_at desc`.
  - **Cron backstop (`app/api/kwikship_sync.js`):** a **2 AM IST cron** (`syncKwikship`) refreshes journeys for **only Kwikship-allocated orders** — identified by EasyEcom's own field **`raw_data->>'courier_aggregator_name' = 'GoKwik Outbound'`** (RapidShyp reads `'RapidShyp- Outbound'`; both ship from the same warehouse so the generated `location` column can't distinguish them). Skips already-final shipments → one Kwikship API call per non-final shipment, zero wasted calls. Manual re-sync: `POST /api/kwikship/sync` (delivery-perf perm).
  - **TWO Kwikship endpoints, used together (added 2026-08-05):**
    - `v1` **auth** `GET /api/v1/shipments/:awb` (headers `gk-app-id` + `gk-app-secret`) → current status, `courier_name`, `shipping_address` (→ zone), `estimated_delivery_date`, payment mode, weight. Scans expose only `{status, description, location, datetime}`.
    - `v2` **public** `GET /track/v2/public?order_code=<awb|order no>` — **no auth at all** (`merchant_id` is accepted but ignored) → the SAME timeline plus **`shipper_remark`**, `shipper_status` and a separate `creation_datetime`/`status_datetime`. It does NOT have a current status, a shipping address (so no zone) or an unmasked phone.
    - ⚠️ **`shipper_remark` is the ONLY human NDR reason either endpoint gives** — "Consignee Unavailable", "Consignee refused to accept/order cancelled", "Delivery Rescheduled by Customer". v1's `description` is a courier code (`UD_EOD-11_Pending`) that means nothing to an agent. Production had stored exactly those codes.
    - **API budget:** `updateKwikshipJourney()` calls **v2 first**, then reads the stored row, and fetches v1 **only when identity is missing** (new shipment, or no stored zone/courier) or v2 failed. Since zone/courier never change once captured, the nightly run costs the SAME one call per shipment it did before — and that call is now the unauthenticated one. The parser accepts both shapes (`shipper_remark → description → status`; `status_datetime → datetime → creation_datetime`), so either source can feed it.
    - The **scan log** (`GET /delivery-performance/shipment/:awb`) also prefers v2, so the Delivery Performance timeline reads "Consignee Unavailable" instead of `UD_EOD-11_Pending`. ⚠️ It serves `raw.status_history` from CACHE first — rows cached from v1 keep rendering codes until that cache is cleared (11 were cleared on rollout; the next view re-fetches v2).
    - **Backfill:** `backfillKwikshipNdrReasons({ dry })` in `kwikship_sync.js` rewrites `ndr_reasons` on rows still holding courier codes. v2-only (no authenticated calls), targets just the rows that match a code pattern (28 of 271 at rollout), touches nothing but `ndr_reasons`, and is idempotent.
    - ⚠⚠ **The webhook was silently undoing the backfill.** The deployed edge fn re-fetched v1 on EVERY event and overwrote `ndr_reasons` with codes — backfilled rows reverted within minutes, a different one each time (proven on AWB 47607612924014, reverted at 08:00:56 by a `rto_in_transit` event; ~148 webhook hits per 6 h). Fixed in `kwikship-webhook` **v7**, which merges v1+v2 exactly like the Node sync. **If NDR reasons ever regress to codes again, suspect the edge function first — it writes far more often than the cron.**
  - The AWB EasyEcom stores (the courier AWB, e.g. Delhivery) resolves directly on Kwikship's `GET /shipments/:awb` (verified: GoKwik AWBs 200, RapidShyp AWBs 404 — so the RapidShyp/DocPharma cron never writes a conflicting row). If an order is re-allocated (e.g. Kwikship→cancelled→RapidShyp), `courier_aggregator_name` updates and it moves to the correct sync automatically.
- **Server-enforced permissions:** UI hiding is cosmetic; every view-specific API group is gated by middleware in `server.js`.
- **Fail-safe reporting:** report dedup lists abort the run when unreadable (never re-spam), and Slack posting is code-disabled (Teams-only) unless explicitly re-enabled.

**Customer Profile — how identity is resolved (get this wrong and the page lies):**
- Keyed on the **last 10 digits of the phone**. Numbers are stored as +91 / 0-prefixed / bare, so any other key silently splits one person into several.
- Sourced from the Shopify **`orders`** mirror, **NOT `b2c_order_easycom`**. EasyEcom writes the placeholder **9999999999** when it has no phone — **4,364 orders across 880 different emails** share that one number, so keying on EasyEcom's phone would fuse 880 strangers into a single profile. - ⚠️ **`orders.name` has a leading `#`, `shipment_journey_ecom.order_name` does not** — joining without stripping it returns **0 rows** (verified: 17,575 with the strip vs 0 without).

- **Identity CLOSURE, not a single lookup.** One person legitimately has several phones and emails, linked through shared orders. Expanding one hop was not enough — starting from different identifiers converged on different answers for the SAME customer (6 vs 18 vs 19 orders), which makes the page untrustworthy. `ordersFor()` therefore keeps pulling on every newly discovered identifier until nothing new appears, so the result is identical whichever identifier you arrive by (verified: 4 entry points → 19 orders / ₹7,835.98 / 2 phones / 3 emails). - **Names.** The Shopify `orders` mirror has **no customer-name column at all**, and EasyEcom's `customer_name` is frequently a placeholder — real orders carry literally `"DUMMY"`. #### Collaboration outreach email (added 2026-08-04)

Draft → optional AI polish → send → ✓, from the **Lists & Campaigns** member table.

- **Subject is fixed brand copy** — `Collaboration opportunity with theelement.skin`. Set server-side in `OUTREACH_SUBJECT` and NOT taken from the client; the field is read-only in the modal and the AI step is explicitly told not to reword it.
- **Body** is the house pitch with variables filled from the saved profile: greeting name (first name only — a trailing `(handle)` parenthetical and emoji are stripped, an honorific keeps the name after it), the sender's own display name, and the fee. **Fee preference: the latest deliverable's `final_price` → `quoted_price`, then the influencer's.** ⚠️ **An unknown fee renders a visible `₹______` blank and is NEVER invented** — the modal warns, and sending with the blank still present asks for a second confirmation.
- **AI polish** (`POST /inf/email/polish`) uses the shared `ai.js` client. ⚠️ **`maxTokens` must comfortably exceed the whole email** — at 1,400 Gemini returned a reply cut off MID-STRING, so the JSON never closed and every polish silently failed; it is 3,000. A **sanity gate** then rejects the rewrite (keeping the user's draft, with the reason shown inline) if it lost the sign-off, lost the `Commercials:` line, or came back under 60% of the original length — a truncated or gutted rewrite must never reach a real influencer. AI is an assist, never a gate: unconfigured or failing simply keeps the draft.
- **Endpoints:** `GET /inf/email/draft` · `POST /inf/email/polish` · `POST /inf/email/send` · `GET /inf/email/log`. All under the existing `/inf/*` permission gate.
- **Thread view + reply tracking (added 2026-08-04).** The **✓ Email sent** control (campaign-list cell and detail-panel chip) is clickable and opens the thread: what we sent plus every reply. `GET /inf/email/thread?influencerId=&refresh=1` — `refresh=1` runs an IMAP poll first, so opening the panel shows a reply that landed seconds ago; `POST /inf/email/poll` is the manual/cron trigger. Replies are stored in the same table with `kind='reply'` + `parent_id`.
  - ⚠️ **Polls the SENDER'S OWN mailbox, not the shared reports one** — outreach leaves from the portal user's address, so the reply lands in their inbox. `pollInfluencerReplies()` groups the sent rows by `from_email` and connects per mailbox with the credentials in `app_user_smtp_ecom` (IMAP host = the SMTP host with `smtp.` → `imap.`, same app password).
  - ⚠️⚠️ **NEVER match a reply by subject.** The outreach subject is fixed brand copy, so every influencer's reply normalises to the *same* thread subject — the first live run of a subject fallback attached **17 unrelated people's replies to one influencer's thread**. Matching is exact keys only: the `In-Reply-To` chain (including reply-to-a-reply, whose Message-IDs are mapped back to their parent) **or** the sender's address equalling the `to_email` we actually wrote to. This is the opposite of the escalation poller, where subject matching IS safe because each escalation has its own subject.
  - Same imapflow trap as the escalation poller: envelopes are collected in one pass and bodies downloaded in a second, because calling `client.download()` inside an active `client.fetch()` iterator deadlocks. Quoted history is trimmed off each reply.
- **Table `influencer_emails_ecom`** — deliberately a LOG, not a boolean: it records to/from/subject/body/`ai_polished`/`message_id`/`sent_by`/`sent_at`, and it works for an influencer with no video row, which a flag on `influencer_videos` cannot. The legacy per-video flag is still written in step so anything reading it agrees.

#### Pincode → City/State autofill (added 2026-08-04)

Type a 6-digit pincode in an address form and City/State fill themselves, **both still editable**. Backend `app/api/pincode.js` → `GET /api/pincode/:pin` (any logged-in user; deliberately not behind a dashboard permission, since every address form needs it). Source is **India Post’s free public API** (api.postalpincode.in — no key, no quota); answers are cached in `pincode_geo_ecom` so a pincode costs one upstream call ever (~400ms first time, ~50ms after). The call is made SERVER-side, which also keeps it clear of the browser CSP.

⚠️ **Choosing the city is the fiddly part — no single API field is right on its own:** District gives "Central Delhi" for 110001 and "Kamrup" for 781001; Block is "NA" (122018), "Gmc" (781001) or "Bangalore North" (560001). The rule is **Division with the postal suffixes stripped** (North/South/East/West/Central/City/GPO/HQ/H.O) → Block → District, which returns the expected city for all 18 pincodes tested across 18 states. Rejected api.zippopotam.us: it 404s on common pincodes (122018) and returns a locality ("Janpath" for 110001) rather than a city, so a wrong-looking autofill would be worse than none.

Frontend helper `ecPincodeAutofill(pinEl, cityEl, stateEl)` (app.js), wired into the two forms that take a real address: **Edit profile** (`infe-*`) and **Send product** (`infsp-*`). It debounces 300ms, fires on input/blur/paste, shows an inline result hint, and **never silently overwrites a value the user typed** — though changing the PINCODE clears that protection, since a new pincode invalidates the old city/state. Failure is quiet and non-blocking: the hint says so and the fields are left alone.

#### Per-user sending mailboxes (added 2026-08-04)

Outreach leaves from the **logged-in user's own address**, not the shared brand mailbox — an influencer's reply has to reach the person who wrote to them. Table **`app_user_smtp_ecom`** (one row per portal user, keyed on the lowercased login email; `smtp_password_enc` is AES-256-GCM, same scheme as `app_email_settings`, and the plaintext is never returned to a client). `sendMailAs(userEmail, opts)` in `email_settings.js` resolves it; `sendMail()` is unchanged and still sends the automated reports from the brand mailbox.

**WHO MAY SEND (`outreachSender()`) — two ways in, nothing else:** (1) a user with their **own** mapped mailbox sends **as themselves**, so the reply reaches them; (2) a **master/admin** with no personal mailbox sends from the **shared brand mailbox**. Everyone else is refused. The check runs **first in the handler, before payload validation and before the already-sent/partnered state checks**, so a permission failure is never masked by a 400 or a 409. ⚠️ **READING is not gated this way** — any user with influencer access can open a thread and read the replies; only SENDING is restricted.

⚠️ **No fallback to the brand mailbox for a NON-admin.** Sending "from" someone with no credentials either fails SPF/DMARC at the provider or quietly misattributes the mail, so an unmapped sender is refused with the exact fix named. The compose modal resolves the mailbox up front and disables Send with that message, rather than letting someone write an email and fail at the last step. A mapping that exists but has no password, or is marked inactive, counts as unmapped.

Admin UI: **Settings → Email & Reports → Sending mailboxes** — every portal user is listed mapped or not, with state chips (Ready / No password / Disabled / Not mapped), map/edit, per-user **Test** (sends that user a mail from their own address), and remove. Blank password on an edit keeps the stored one. Gmail/Workspace need an **app password**. Endpoints `GET|POST /api/admin/user-mailboxes`, `DELETE /api/admin/user-mailboxes/:email`, `POST /api/admin/user-mailboxes/test` — all admin-only.

**Bank statement import** (Data Entry -> *Bank statement* tab). Upload an `.xlsx`/`.csv`; the header row is found by looking for the columns rather than a fixed offset. Every line gets a suggested ledger **with its reasoning and a confidence score**, from `tally_bank_match.js` — measured **98.8% correct with 0 wrong ledgers** leave-one-out against this company's own 161 bank vouchers. Ranked: a learned rule > the same narration seen before > exact party name > fuzzy name > distinctive wording. It returns **nothing** rather than guess, because a wrong ledger costs more than a blank one.

Safeguards: the bank's own **running balance is re-derived for every row** (a free proof the parse missed nothing); each line is hashed on date+amount+narration+ref into `tally_bank_lines_ecom` with a UNIQUE index, so **re-uploading an overlapping statement cannot double-book**; rows dated before the company's `BooksFrom` are refused with an actionable message instead of creating drafts Tally would reject; and the import stays **disabled while any chosen ledger does not exist**. Confirmed rows become ordinary DRAFT vouchers. Every correction is stored in `tally_bank_rules_ecom`, so the same narration is never asked about twice.

**An under-80% match never becomes a draft on its own.** The matcher's confidence is a *lead*, not a decision: below `CONFIDENT = 0.8` the row is shown with its percentage and reasoning but the ledger field is left **blank**, so it counts as unmapped until a person picks one. Accepting it is still one click — the picker carries it at the top as an amber **"Suggested · 72% — VIVE COSMETICS / too unsure to fill in for you"** entry — but it has to *be* a click. Neither that entry nor a "create ledger" entry is ever pre-selected, so Enter can't commit something nobody looked at. Enforced **again server-side** in `/tally/bank/import`, which re-derives the suggestion rather than trusting the browser and refuses any row whose submitted ledger equals a sub-80% suggestion without `confirmed: true` (*"only 72% sure of X — confirm it on screen before it can become a draft"*); a rule enforced only in the page is not enforced at all, since a stale tab or a replayed request walks straight past it. Verified end-to-end against the live route with a deliberately misspelled payee: refused unconfirmed, **claimed no bank line on the way out** (so the statement row stays mappable), and accepted once confirmed. ⚠️ On the FY 2025-26 statement this rule currently changes nothing — **all 994 narrations score either ≥80% or produce no suggestion at all**, so there is no sub-80% row to catch; the guard is for future statements and companies where fuzzy name matches do appear.

**Narration labels — telling apart two kinds of transaction on one running account.** A service partner's ledger carries transactions that mean opposite things but whose bank narrations look identical: with RapidShyp (`Open Source Business Solutions Pvt. Ltd.`), money **out** is a wallet **Recharge Topup** and money **in** is a **COD Remittance**. Direction is the only thing that distinguishes them, so `tally_narration_labels_ecom` keys a label on `(company, ledger, direction)` and the bank import prefixes it: `COD Remittance | NEFT CR-ICIC0SF0002-OPEN SOURCE…`. The label goes at the **front** on purpose — Tally shows a limited amount of narration, and the label is the part worth keeping when the reference number is cut off. Two details that matter: the learned mapping rule is still built from the **original** bank wording (matching on our own label would teach the matcher a pattern that never appears in a real statement), and re-labelling is idempotent, so a re-import or an edit can't stack `COD Remittance | COD Remittance | …`. Managed via `GET/POST /tally/narration-labels` and `DELETE /tally/narration-labels/:id`; POST refuses a ledger that doesn't exist in the company, since the label would otherwise silently never fire. No UI yet — labels are set through the API.

**The pending pile — mapping a statement over several sittings.** A big statement is not mapped in one go, and originally an unmapped line existed only in the browser tab that parsed the file: closing it meant re-uploading the whole statement to get back to "what is still unmapped". Every uploaded line that has not become a voucher is now kept in `tally_bank_pending_ecom` (UNIQUE `line_hash`, same identity as the imported-lines table, so **a line is in exactly one of the two at any moment** — pending or booked). The *Bank statement* tab then opens with **"N row(s) from an earlier upload are still waiting to be mapped → Continue mapping"**, which serves the saved rows through `GET /tally/bank/pending` in the same shape `/parse` returns, so the review screen renders them unchanged. Importing removes the line from the pile; deleting or releasing a voucher **puts it back** (with the deletion reason), so pulling a doubtful entry out of the register returns it to the mapping list instead of it vanishing until the next upload.

Suggestions are **recomputed on every read, never stored**: as ledgers get created and corrections learned, a row that was unmatchable last week can become obvious, and a stored guess would go stale. Rows dated outside the books are kept in the pile too — they become importable the moment `Books beginning from` is widened in Tally, and dropping them would hide the problem. The saved list shows an indigo banner instead of the running-balance verdict, because a partial statement has gaps by design and asserting either way would mislead. `GET /tally/bank/pending/count` backs the badge.

**The ledger picker is hand-drawn, not a `<datalist>`.** The browser renders a datalist popup itself, so it ignores the page completely: on a dark-mode machine it painted a **black panel over the light UI**, sized itself to the longest ledger name, and listed every ledger at once — on a 28-ledger company that covered the whole viewport. None of it is styleable. It is now one shared panel (120 inputs can be on screen; 120 panels would fight for z-index), positioned under the focused field and flipped above it when the row sits low, with arrow-key/Enter/Escape navigation and the group shown under each name. Focusing a row that already has a ledger lists **everything** with that one highlighted, rather than filtering down to the single value you are trying to change. ⚠️ `app/static/tailwind.css` is **pre-compiled and there is no build script**, so only classes already in that file work — `hover:bg-indigo-50`, `hover:bg-slate-50` and `last:border-0` are not in it (this is why the older SKU combobox at `app.js` ~9798 has a dead hover). The picker therefore drives its highlight from JS, which also means the mouse and the arrow keys move the *same* selection instead of showing two.

**Creating a ledger from a NO MATCH row.** On a fresh company most lines have no ledger yet (185 of the 199 pending rows), so the picker offers **`+ Create ledger "NAME"`** rather than dead-ending — and pre-fills the name with the payee read out of the narration, so a party ledger is one click instead of retyping. Choosing it opens the group picker for that single name, because a ledger created without a group is precisely the failure this feature exists to prevent (Tally files it under Suspense). A create entry is **never pre-selected unless it is the only option**, so Enter can't invent a ledger nobody looked at. `newLedgerCandidates()` in `tally_bank_match.js` builds the names — kept **separate from `extractParty()`** on purpose: that one feeds the matcher, where a spare candidate is harmless because it simply fails to match, whereas these are shown to a person and a bad one costs attention. It reads `<gateway ref>/<merchant>` (`K4RHQ54EAR62LNOXD4/PAYUOPENSOURCEBUSINE` → `PAYUOPENSOURCEBUSINE`), offers **both halves** of `TPT-<purpose>-<person>` since the purpose is often not a ledger, drops a candidate that is another with junk bolted on the front, and holds `extractParty`'s catch-all "longest alphabetic run" back as a **last resort** (it reads a NEFT line as `CNRB RAKESH SHARMA NETBANK HDFCN UPTODATE` — good to match against, terrible as a ledger name). Measured on the live pending set: **184 of 185** unmatched rows get a usable name, only 21 need a choice between two. Leave-one-out re-run after the change: **still 98.8%, 0 wrong**.

**⚠️ The group is as important as the name — and `propose` used to lie about it.** A ledger's GROUP decides which statement it lands in. Paying a **Sundry Creditor** that was never invoiced records *no expense at all*: it leaves a debit balance sitting on the balance sheet, so profit is overstated and a phantom receivable appears. The same payment under **SALARY** or **INFLUENCER MARKETING EXPENSES** correctly hits the P&L — and is what the CA's TDS (192 / 194C / 194J) and GST workings are built from. `/tally/ledgers/propose` detected the right precedent group but, when that group did not exist in the target company, **silently substituted `Sundry Creditors` while still printing the reason "sits under INFLUENCER MARKETING EXPENSES in your other company"** — the screen said one thing and did another. Worse, the modal's group `<select>` only listed *existing* groups, so a proposed new group matched no option and the browser selected the first one (**Bank Accounts**). Fixed: the proposal now returns the real group plus `needsGroupCreating` + `groupParent`, the dropdown carries it as *"— will be created"*, and `POST /tally/ledgers` accepts a `groups: [{name, parent}]` list which it creates (via the new `buildGroupCreateXml`, a `<GROUP>` master import) **before** the ledgers, re-syncing the group mirror in between. Found by auditing the first mapped month: **9 ledgers across 28 vouchers** were filed as Sundry Creditors that FY 2026-27 files under SALARY or INFLUENCER MARKETING EXPENSES — the two groups FY 2025-26 was missing.

**Sales & GST from the filed GSTR-1 (FY 2025-26).** A bank statement gives receipts and payments; it cannot give sales, purchases or GST, none of which pass through the bank as separate entries. Without them the marketplace ledgers carry the money received as a credit with no sale behind it (₹72,97,063 at one point) and the P&L shows expenses against **zero revenue**. FY 2025-26 sales were therefore built from the **filed GSTR-1 returns** — the authoritative source, and the one that guarantees books = returns at assessment. The **JSON** download (Returns Dashboard → GSTR-1 → DOWNLOAD → GENERATE FILE) is essential: the PDF gives only table totals, and deriving the rate split from those silently fails once more than one rate is in play. Sep–Mar carried **5% sales alongside 18%** (ayurvedic/medicament HSN 3003/3004 next to cosmetics), growing from ₹6,279 to ₹4,45,899 a month — invisible in the summary, and the reason a pure-18% derivation came out ₹3.2 lakh short in March. `b2cs[].sply_ty` gives INTER/INTRA outright; B2B direction is read from whether the line carries `camt` (intra) or `iamt` (inter). Every month is reconciled against its own filed PDF **before** a voucher is produced; a month that doesn't tie is skipped, not booked. Result: 10 monthly Sales vouchers, Jun–Mar (Apr/May were NIL returns), totalling **₹99,45,790.37 sales + ₹16,00,970.60 GST**, matching the filed returns exactly. ⚠️ **Table 14 (supplies through an ECO) is NOT booked** — it is a *disclosure* of how much of Table 7 went through Amazon/Flipkart so the department can cross-check their TCS, not additional supply. In July it equals 100% of Table 7, so booking both would double that month's sales.

**Where this format differs from the CA's.** FY 2026-27 raises one Sales voucher **per marketplace** (Amazon / Flipkart / Shopify), debits that marketplace's own ledger, and adds a `ROUND OFF` line. That is better in one respect — the sale clears against the receipts already sitting on those ledgers. It cannot be reproduced from GSTR-1, which summarises B2C by state and rate only and never names the marketplace; splitting it would mean inventing an allocation. So FY 2025-26 books one monthly voucher per month to a single `ECOMMERCE RECEIVABLE` (Sundry Debtors), and the marketplace accounts are cleared against it with one year-end journal.

**Opening a fresh set of books** — a new company has only `Cash` and `P&L A/c`. `POST /tally/ledgers/propose` suggests a group for each missing counterparty **by looking at how the same name is filed in your other company**, which carries the knowledge across without copying data between two deliberately separate companies. `POST /tally/ledgers` then creates the confirmed ones via a real Tally master import. This is the safe inverse of the hazard the project guards against: the operator names the ledger and picks its group, rather than Tally inventing it under Suspense.

| Voucher Register | `finance-register` | Audit trail: every voucher with status pills (draft/queued/posting/posted/failed/cancelled), Tally voucher no., filters (status, date range, free text) → detail drawer showing the ledger entries, Tally's own error text, and the **exact request + response XML**; Retry / Cancel. It reuses the bank tab's ledger picker via `data-pickmode="plain"`, loads the *voucher's own* company's ledgers (tracked in `_fb2.ledgerCompany`, deliberately **not** `_fb2.company` — that one drives the bank tab's dropdown and decides which books an import posts into), and **refuses a ledger Tally doesn't have**, since that is exactly what gets auto-created under Suspense at posting time. It swaps only the line naming the current party: identifying the bank side by a `/BANK|CASH/` guess would rename *every* line the moment the guess failed, putting both sides of the voucher on one ledger. **Sorted oldest transaction first by default** (`sort=date_asc`), with date ↑↓ / amount ↑↓ / recently-entered in the filter bar — the previous `created_at DESC` ordered by *when the row was keyed in*, which is meaningless after a bank import where hundreds of rows share one timestamp and their order is really just the order the spreadsheet was walked. `created_at` remains the tie-breaker so paging is stable when many rows share a date; an unknown `sort` value falls back to the default rather than erroring. Changing the sort **clears the selection on purpose** — the list is capped, so a different order can return a different set of rows, and a tick surviving into a batch the operator can no longer see is how the wrong voucher gets posted. When the cap is hit the register says so (*"Showing the first 1000 only"*) instead of quietly truncating, because the status counts and "select all" then describe only what is listed. A **checkbox column + "Post N to Tally"** bar handles the bulk case (importing a year's statement leaves hundreds of drafts); it shows the selected count and value, warns in red if the selection spans **more than one company**, and posts in chunks of 25, halting on the first failure. Only an admin sees it, and the server enforces that regardless. **Admins additionally get "Delete entry"** — a real delete, so clearing a junk entry never means opening the Supabase SQL editor. It removes only our row and **never touches Tally**: a voucher already in Tally must be removed there (Alt+D), and the dialog says so rather than leaving the two silently out of step. Refused while a voucher is `queued`/`posting`/`awaiting_approval` (the agent could be mid-post, or it belongs to an open batch — reject the batch first). A reason is **required** when the voucher had reached Tally, optional otherwise. Every delete snapshots the whole voucher — ledger lines, who entered it, who removed it, why — into `tally_voucher_deletions_ecom`, shown as a **"Deleted entries"** panel any finance user can read |

**Optional-voucher dry run:** the Data Entry panel has a **Post as Optional** toggle → `<ISOPTIONAL>Yes</ISOPTIONAL>`. Tally records the voucher in the **Day Book** but excludes it from the P&L, balance sheet, ledger balances and GST returns until a human marks it regular inside Tally. This is the correct way to validate the write path **against real books** — the round-trip is genuine, the accounts are untouched. It is not a stored column: the flag lives in `request_xml` (the audit record), and the Register badges it by reading the flag back from there, so a retry stays faithful to the original intent. The confirm dialog changes wording and drops its danger styling when the toggle is on.

**Nightly batch push (23:50 IST) with Teams approval — the normal route to Tally.** Non-admins cannot push at all; their entries reach Tally like this:

```
day        user enters vouchers  →  saved as `draft`   (Tally never contacted)
23:45      cron warms the Tally masters
23:50      cron re-validates every draft, groups the VALID ones into a batch (ref TB-YYYYMMDD-n),
           sets them `awaiting_approval`, posts an approval card to the Teams finance channel.
           Invalid ones stay `draft` with `validation_error` and are listed as **Blocked** — one
           typo never blocks the rest, and fixing it puts the voucher in the next run.
admin      replies **yes** in Teams (or Approve in Finance → Voucher Register) → vouchers → `queued`
+seconds   the bridge agent posts each one and acks Tally's raw reply
watcher    once all are terminal → result card ("Posted 12 of 12" / per-voucher Tally errors)
```

Exception cards cover the paths that would otherwise fail silently: **bridge offline** at 23:50 (batch held, nothing lost), a batch **stalled >1 h**, **every draft blocked**, **expired unapproved** (vouchers return to `draft`), and *approved but `TALLY_POST_ENABLED` is false*. The batch lives in `tally_push_batches_ecom`, **not** a memory variable — unlike the Amazon review approval, it survives a restart. Teams approval is recognised as bare `yes`/`no` (unambiguous in a dedicated channel) or `approve TB-20260730-1`, so a stale card cannot be approved by accident.

⚠️ **Teams gives the listener no role information**, so *membership of the finance channel IS the approval boundary* — only admins should be in it. Dashboard approval is separately gated on `role=admin`.

**Sharing one channel with the Amazon review approval is supported** (the live setup does exactly this — both point at `cron_confirmation`). Two things make it safe: the poll loop maps channel → flows and fetches each channel **once** (fetching twice would be a bug, not just waste — `lastSeen` is keyed by channel id, so the first read advances the watermark and the second sees nothing), and `parseApproval()` requires the command to be the **whole message**. That second rule matters more than it looks: a loose `/^no/` would treat *"no idea what happened there"* as a rejection, which in a channel where people actually talk **will** happen. Routing: an explicit target wins (`tally yes`, `amazon no`, `approve TB-20260730-1`); a bare `yes`/`no` goes to whichever flow is genuinely pending (`hasPendingBatch()` / `hasPendingReview()`); if **both** are pending it actions nothing and replies asking which, quoting the batch ref so the answer is copy-pasteable. Nothing pending → silence.

Optional `TEAMS_WEBHOOK_FINANCE_RESULT` sends result/exception cards to a different channel from the approval request, so routine confirmations need not sit in the admin channel.

**Capability:** posting is a separate right from drafting — `finance-post-tally` (see §6). A user with only `finance-entry` can compose, validate and preview a voucher but the Post button is disabled, and the server refuses `/tally/vouchers/:id/post` regardless of the UI.

Backend: `app/api/tally.js` + `app/api/tally_xml.js`; tables `tally_vouchers_ecom`, `tally_masters_ecom`, `tally_bridge_status_ecom` (§8); integration notes and the mode/kill-switch behaviour in §10.

## 6. Authentication & Authorization

- **Login:** `POST /api/login` — checks the `.env` bootstrap admin first (never lockable), then `app_users_ecom` (scrypt-hashed passwords). Returns a **6-hour** JWT with `{ sub, role, permissions[], name }`.
- **6-hour session + auto-logout:** JWTs expire after 6h (`SESSION_TTL` in `auth.js`). The client reads the token's `exp` and proactively logs the user out the instant it passes (`scheduleAutoLogout()` in app.js), and drops an already-expired token on page load; any API 401 also forces logout. Re-armed on every fresh login and silent token-restore.
- **Sign-out flow:** the manual **Sign Out** button runs `signOut()` — a ~2.5s branded loader (logo), then a **"Signed out successfully" confirmation page** (`#signout-view`, thank-you + "Click here to log in") rather than snapping straight to login. `_clearSession()` also **drops the `#view` hash** so the next sign-in lands on the **home** dashboard (not the page they signed out from). Silent logouts (expiry / 401 / auto-logout) still go straight to login via `logout()`.
- **Activity logging:** `logActivity(event, view)` (app.js, fire-and-forget, `keepalive`, 2s per-view debounce) POSTs `/api/activity` on every `navigate()` and on login → `user_activity_ecom` (email from the token, never the body). Powers the **User Analytics** dashboard.
- **Welcome popup:** after a successful sign-in (password-only or OTP), a ~3.4s **dark-premium greeting card** floats over the dashboard, which stays visible but **blurred + dimmed behind** (a modal, not a full-screen takeover). Layout = time-aware greeting ("Good morning/afternoon/evening", no emoji) + the user's **display name** (gradient-shimmer hero) + "Welcome back to Ecom Central"; glowing logo ring + sparkles (`showWelcomeSplash` / `_wsGreeting` in app.js). When no name is set it shows "Welcome back" as the hero and the email as subtext. Not shown on silent refresh-restore. The name is admin-editable on the Users page (`app_users_ecom.name`); the `.env` bootstrap admin's name comes from `APP_USER_NAME` **or, if that's unset, falls back to the `name` on its own Users-page row** (`adminName()` in auth_routes.js) — so setting the name in the portal is enough, no `.env` change needed.
- **2FA (added 2026-07-16 for admins; switched from MSG91 SMS to EMAIL OTP and extended to ALL accounts 2026-07-17):** when the portal can send mail (Settings → Email / `app_email_settings`, sender `digital@theelement.skin`, falling back to `.env` `EMAIL_*`), `/login` for any user does not return a token — `app/otp_mail.js` generates a 6-digit OTP, stores only its HMAC-SHA256 hash in a 5-minute in-memory record (max 5 wrong attempts, single-use, 25s server-side resend throttle — a duplicate `/login` inside the gap **reuses** the in-flight OTP instead of erroring; a pm2 restart just voids pending OTPs), emails it via the shared `sendMail`, and `/login` returns `{ otp_required, otp_token (5-min pre-auth JWT, stage:'otp2fa', no permissions), email_hint }`. The client then calls `POST /api/login/verify-otp { otp_token, otp }` → real JWT (role/permissions re-fetched fresh from DB, never trusted from the pre-auth token), or `POST /api/login/resend-otp`. Both are public + rate-limited. OTP mails carry **no CC** (`cc: []` — the default report CC from Settings is explicitly excluded), and after expiry each OTP email is **auto-purged from the sender's Sent folder** over IMAP (moved to `[Gmail]/Trash` + expunged; a plain expunge in Sent would only archive on Gmail) — scheduled at send-time +5m15s, plus startup sweeps at +60s/+6.5m to catch purges lost to a restart. If email/SMTP isn't configured, logins fall back to password-only with a server-side warning — never a lockout. **Emergency 2FA off-switch:** blank the SMTP settings (or fix SMTP) — there is no separate 2FA env var. The OTP email shows the Ecom Central logo as a hosted image (`DASHBOARD_URL/static/assets/ecom-logo.png`, not an attachment — no Gmail attachment chip).
- **Signup:** `POST /api/signup` — open signup creates a **pending** account; an admin must approve and grant dashboard permissions. **Mobile (Indian 10-digit) is mandatory** on signup, admin add-user, and editable per-user (`POST /admin/users/:id { mobile }`).
- **Rate limiting:** per-IP (`req.ip`, trust-proxy aware) + per-account (10 attempts / 15 min); bootstrap admin exempt from the account limit.
- **RBAC:**
  - Admin (`role=admin` or permission `*`) → everything.
  - Users hold an array of permission keys — **dashboard-view keys** (see §5) plus **capability keys** that grant an action without full admin. Capability keys (Users page → "Actions" group): **`send-escalation-emails`** — lets a non-admin **send escalation/critical/claims emails** (✉️ Send critical email, ✉️ Escalate all to RapidShyp, Silent-RTO/Late/In-transit claim sends); **`support-cancel-order`** (2026-07-29) — lets a support agent **Cancel a held order** from the Call Queue (cancels on Shopify + refunds any online-paid COD fee); **`finance-post-tally`** (2026-07-30) — *superseded:* pushing to Tally now requires **`role=admin`**, not a capability key. The key is retained so existing grants don't error, but `requireAdminPush` in `tally.js` and `requireAdmin` in `tally_batch.js` are the real gates — a non-admin holding the key still gets a 403. A non-admin drafts; the nightly batch is how their entries reach Tally, after an admin approves. Only the admin can grant them. Email **Settings** (SMTP creds) remain admin-only.
  - **Server-side enforcement** (`server.js`): a path-prefix middleware maps API groups → required permission, e.g. `/delivery-performance` → `delivery-perf`, `/silent-rto-claims|late-deliveries|intransit-late` → `claims-sla`, `/order-marks|likely-fake-insight` → `delivery-perf`, `/docpharma` → `docpharma-recon`, `/fba/` → `amazon-fba`, `/ops-control` → `ops-control`. The shared shipment-detail endpoint accepts *either* `delivery-perf` or `claims-sla`. Mount-level `requirePermission` guards `/api/amazon` and `/api/fulfillment-ops`. `/tally/vouchers/:id/post` → `finance-post-tally`, the rest of `/tally/` → `finance-entry`/`finance-register` — **but that rule is written `/^\/tally\/(?!bridge\/)/i`**, because listing `/tally/bridge/` in `PUBLIC_API` only skips the JWT gate: this permission middleware still runs, and a key-authenticated request carries no permissions, so a broad rule would 403 the bridge agent. Any future non-JWT route group needs the same exclusion. **The 6 email-send routes** (`/critical-email/{compose,polish,send}`, `/silent-rto-claims/send`, `/late-deliveries/send`, `/intransit-late/send`) are gated by `requirePermission('send-escalation-emails')` (admins pass via `*`); the claims sends additionally sit behind the `claims-sla` view gate. `/api/admin/*` requires `role=admin`.
- **JWT secret hygiene:** the app refuses to boot with a missing/weak `JWT_SECRET` (<32 chars or known-default).

  - **📦 Inventory-movement ledger + 4-bucket reconciliation (2026-07-23):** EasyEcom's `availableInventory` excludes not just reserved but ALSO stock physically on the shelf in a non-sellable state. Full equation: **Physical = Available + Reserved + Blocked + Awaiting-putaway**; **True variance = Physical − all four** = real shrinkage. Fed by a webhook **movement ledger**: table **`inventory_movements_ecom`** (`event_type` grn/adjustment/return, sku, qty, adjustment_type, old_status→new_status, bins, ref, raw) + edge fn **`easyecom-inventory-webhook`** (verify_jwt OFF, version-controlled in `supabase/functions/`). Token field can be anything (endpoint doesn't enforce it unless `EE_INVENTORY_WEBHOOK_TOKEN` is set). **`bucketBalances()`** derives current **Blocked** (net units moved INTO a non-Available status: Damaged/QC-Fail/Expired/Lot-Locked) + **Awaiting-putaway** (returns received − putaway adjustments — the limbo where returned/cancelled stock is physically in but not yet binned into system Available) per SKU. `POST /inventory/count` freezes reserved+blocked+awaiting at count time (cols `blocked_qty`, `awaiting_putaway_qty`); Count Analysis shows Avail · Reserved · Blocked · Await · Adj-sys · Physical · True-diff. **⚠️ Blocked & Awaiting are running ledger balances that firm up as webhook events accumulate** (and once the status/adjustmentType classification is verified against real payloads). For a perfect reco: blind, by-bin, idle-time counts + freeze all buckets at the count instant + post confirmed variances back as EasyEcom adjustments (which re-flow through the ledger).

| — (not a cron) | **RapidShyp "unknown AWB" handling (2026-08-03)** — `enrichAWBsBackground()` in `fulfillment_ops.js` asks RapidShyp about every AWB found on a Shopify fulfillment, but the catalogue is multi-courier, so shipments booked with **Delhivery direct / GoKwik(Kwikship) / DocPharma** come back **HTTP 400 "unknown AWB"**. | `0 9 * * *` (`CRON_DIGEST_SCHEDULE`) | **Cron digest → Teams "Cron Response"** (2026-08-01). Every job runs through `cronJob()` → `runCron()` in **`app/api/cron_report.js`**, which times it, catches what it throws, **and also intercepts `console.error` for the duration** so errors a job swallowed itself (`.catch(e => console.error(…))` — most of them do) are still reported. **Attribution is by LOG TAG (2026-08-03):** a captured line counts only when its own `[Tag]` matches the job name (names are derived from that same tag, so `ShopifyHold (*/2 * * * *)` accepts only `[ShopifyHold…]` lines). Without this a long job absorbs whatever overlaps it — `ShopifyHold` runs ~43s and was reported FAILED because of `[RS Sync] … 400` lines that were never its own. Lines from another job, or untagged, are ignored (that job reports its own); a **thrown** error is always attributed regardless of logging, so a genuine crash can't be missed. **A FAILURE posts an immediate ❌ card** (job · time · duration · reason); **successes are counted and rolled into this one digest** (runs · ok · failed + last error per job). Why not a card per success: the 26 jobs fire **~1,800×/day** (two `*/2` jobs alone are 1,440), which would bury the failures. Modes via `CRON_REPORT_MODE`: `digest` (default) / `all` (a card per run) / **`failures`** (failures only, no digest — silence means healthy; **this is what live runs**) / `off`. **`all` is impractical in practice — measured 1,748 cards/day, one every 49s** — because the two `*/2` jobs alone are 1,440 of them and both are usually instant no-ops (they return the moment their feature flag is off), so real failures get buried; `CRON_REPORT_SKIP` (comma-separated, case-insensitive substrings of the job name) mutes the SUCCESS card for named jobs under `all` only — **failures are never muted**, a skipped job still posts the instant it fails. Suggested if using `all`: `CRON_REPORT_SKIP=TallyBatch,ShopifyHold,EE Session,EscMail` → ~66 cards/day. ### Teams channel reports (Adaptive Cards)

**Tabular data — the `table` block (added 2026-08-04).** Neither obvious way of showing a table in Teams works: a ```` ``` ```` code fence renders as **literal backticks with the whitespace collapsed** (so hand-padded columns arrive as a ragged single-spaced list), and Adaptive Card 1.5's native `Table` element is unavailable because the Workflows connector pins **1.4**. The card path lays it out **column-major** — one `ColumnSet` whose N columns each hold a stack of TextBlocks (header + every value for that column) — because separate per-row ColumnSets do not align to each other, while columns sharing one container width do. Cells default to **`align: 'Center'`** (override per column with `'Left'`/`'Right'`). ⚠️ **In the HTML twin, alignment must go on the legacy `align` attribute** — Teams' sanitizer strips `text-align` out of an inline `style` on `<td>`, which is why an early version had only the header row centred (that was Teams' own default `<th>` styling, not ours).

### Engineering gotcha — router-level response caches
`ops_control.js` and `amazon_fba.js` keep 5-minute GET response caches via `router.use(...)`. Because those routers are mounted at `/api`, an **unscoped** `use()` runs for every `/api` request that falls through them and silently caches *other routers'* GET responses (this once froze all `/support/*` reads for 5 minutes — "DB changed but dashboard shows old data"). Both middlewares are now path-guarded (`/ops-control`, `/fba`) — never widen those guards, and scope any future `router.use()` middleware to its own path prefix.

### `.env` sync
`.env` is not in git. When new variables are introduced (see §12 — most recently `AI_*`, `EMAIL_ENC_KEY`, `TEAMS_*`), copy them to the server's `.env` manually before restart.

### HTTPS

### Bug fixes 2026-08-05 — stale HOLD chips + notes leaking between Support panels

**1. Released / delivered orders kept showing a HOLD chip.** `/api/ee-hold-marks` (which drives the HOLD chip on EVERY dashboard) treats EasyEcom's `raw_data.order_status_id = 44` as On Hold — but ⚠️ **EasyEcom leaves that id at 44 even after the order ships**; its own `order_status` text moves on to "Shipped" while the id does not. The endpoint only dropped **cancelled** orders, so a released-then-shipped order stayed chipped forever. Measured before the fix: 6 orders still flagged as held, **all already shipped, 4 of them delivered/RTO**. It now also drops a hold once the order shows a courier scan (`MOVED_RE` on `tracking_status`), a `fulfilled` state, or a cancellation → 41 chips, 0 terminal. ⚠️ **An AWB alone is deliberately NOT a drop reason** — an order can be genuinely held in EasyEcom after the AWB is assigned but before pickup (the Call Queue treats that state as holdable), so dropping on `awb_number` would hide real holds. Note the stale `order_status_id = 44` rows remain in `b2c_order_easycom`; this fix filters them at read time, so anything else reading that field directly needs the same guard.

**2. Call-Queue notes surfaced on the Undelivered panel.** A note is scoped to the panel it was written in, not to every panel that later shows the order — a "confirmed" note added pre-dispatch was reappearing days later on Undelivered, where it reads as a statement about the delivery (real case: TE25-37934, note 27 Jul 08:35, first seen undelivered 30 Jul 06:42). The boundary is **`undelivered_tracking.first_seen_at`**: the Undelivered / Status-changed panels show only notes written AT OR AFTER it, the Call Queue only those written BEFORE. Derived from timestamps already stored rather than a new `context` column — a column would only scope notes written from that day on, while this scopes all 2,105 historical notes correctly with no migration. **Display scope only: no note is deleted**, and the order-detail modal still shows the full history. Impact measured: of 325 notes on ever-undelivered orders, 284 stay on Undelivered and 41 move back to the Call Queue.

## 16. Security

Hardening completed in the 2026-07 security audit:

- **Transport of secrets:** `.env` git-ignored; all secrets flow through `config.js`.
- **Auth:** scrypt hashing (timing-safe compare), strong-JWT-secret enforcement, 1-day token expiry, per-IP + per-account login rate limiting.
- **AuthZ:** server-side per-dashboard permission gates (path-prefix middleware + mount-level `requirePermission`) — UI hiding is never the only control.
- **CSP:** `script-src 'self' 'unsafe-inline'`, no external CDNs (Tailwind compiled, Chart.js self-hosted), `object-src/base-uri/frame-ancestors/form-action` locked, `connect-src 'self'`.
- **XSS:** `escapeHtml`/`ecEsc` applied to customer-data render sinks in the SPA.
- **Injection:** PostgREST filter injection fixed (`.or(name.eq.X)` → `.in()`), webhook IDs validated (`/^[\w-]+$/`).
- **Secrets at rest:** portal SMTP password AES-256-GCM encrypted (`crypto_util.js`, versioned format `v1$iv$tag$ct`, tamper-detected); `app_email_settings` and `order_marks_ecom` are RLS-locked with no client policies (service-role only).
- **Fail-safe messaging:** Slack hard-disabled (`SLACK_ENABLED` opt-in); report dedup aborts on ledger read failure instead of re-spamming.

**Known open items**
